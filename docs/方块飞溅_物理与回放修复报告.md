# 方块飞溅（BBS Block Splash）—— 物理与回放修复报告

> 目标：从第一性原理出发梳理插件，修复"方块不跟随物理运动、原地随意抽搐"这类 bug，
> 并让物理行为符合 BBS 的回放规则（为短片拍摄服务）。

---

## 一、第一性原理梳理

### 1.1 插件在系统里的位置

把插件拆到最底层的三个事实：

**事实 A：Minecraft 原版只有一种"方块运动"原语 —— `FallingBlockEntity`。**
方块本身不能动，实体能动。所以"让方块飞"这件事在实现上只有一条路：
**方块 ↔ 实体双向转换**。整个插件的一切都是这条转换的编排。

**事实 B：BBS 提供"时间轴编排系统"，但只编排实体，不编排世界方块。**
BBS 的 `ActionClip` 是回放时间轴触发动作的统一入口，本插件注册 5 个自定义 ActionClip
（`block_splash` / `block_shockwave` / `block_splash_reverse` / `block_path` / `block_splash_combo`），
于是 BBS 的时间轴、关键帧、编辑器 UI、`DamageControl` 全部零成本为它们工作。

**事实 C：短片工具的硬性要求是"可定格、可倒拖、可复现"，不是"看起来像"。**
这一点决定了插件不能按"游戏玩法"的方式写物理 —— 见下节。

### 1.2 由事实 C 推出的四条不可违背的约束

| 约束 | 含义 | 违反后的表现 |
|---|---|---|
| **C1 服务器 20 TPS 是权威** | 只有服务端知道刚体真实轨迹 | 客户端"猜"出来的位置会漂移 → 抖动 |
| **C2 渲染帧率与 tick 无关** | 60/144/165Hz，BBS 导出甚至是任意固定帧率 | 任何依赖"逐帧 dt"的实现都会随帧率变形 |
| **C3 网络不可靠** | 位置包会丢、会合并、会晚到 | 任何"开环预测 + 比例校正"都是正反馈回路 |
| **C4 回放时钟是唯一时间轴** | 暂停不推进，拖动逐 tick 行走，导出可复现 | 物理与时间轴脱钩 → 无法拍摄 |

**这四条直接把正确方案锁死了**：

```
物理：只在服务端跑，用固定步长，由回放时钟驱动（C1 + C4）
渲染：客户端只做"已确认权威样本之间的插值"，纯函数、无状态（C2 + C3）
生命周期：特效的存续范围 = 片段的范围（C4）
```

原插件在**数据流分层、恢复保险、参数体系、UI 体系**上做得很好，
真正的问题集中在两处：**客户端渲染做了不该做的开环预测**，
以及**物理步进挂错了时钟**。

### 1.3 一次"方块飞溅"的正确生命周期

```
用户放置 block_splash 片段
        │
        ▼ 回放走到片段起始 tick（ActionClip.applyAction，全局只触发一次）
① 收集区域方块 → ② 抽样 → ③ 记录原始状态并清空 → ④ 注入承力几何为静态碰撞体
→ ⑤ 按形状算初速度 → ⑥ 建刚体 + 生成 PhysicsBlockEntity
        │
        ▼ 之后每个回放 tick（ActionClip.applyRange）
⑦ driveTo(localTick) → 刚体步进 → 实体读变换 → 同步到 MC 实体 → 记录
   暂停回放 → applyRange 不被调用 → 物理定格
   向后拖动 → 按保存的初始条件重建刚体，重新模拟到目标 tick
        │
        ▼ 回放停止（ActionPlayer#stop，所有结束路径的唯一汇聚点）
⑧ 销毁该影片的物理世界与实体（DamageControl 同时恢复方块）
```

## 二、Bug 根因清单（症状 → 根因 → 证据）

> 以下"证据"均为修复前源码中的真实片段。

### R1 · 渲染位置在两个数据源之间逐帧切换 ★核心

`PhysicsBlockEntity.getRenderX()`：

```java
if (this.predInitialized && !this.predictionSkippedThisFrame) return this.predX;
return this.prevClientX + (this.clientX - this.prevClientX) * tickDelta;   // 另一套值
```

`tickAdvanced` 只在客户端 tick（20Hz）置 true，`updatePredictionFromTickDelta` 每渲染帧消费并置 false。
60FPS 下每 tick 的第 1 帧用 `predX`、第 2/3 帧用 lerp 值 —— **两者数值完全不同**，
方块就在这两个位置之间以 20Hz 频率来回跳。

**这就是"不跟随物理运动、随意抽搐"最直接的来源。**

### R2 · 预测积分实际上被"冻结"了

`tickAdvanced` 每 tick 只置位一次、每渲染帧消费一次，于是每 tick 只有**第一渲染帧**真正
执行 `updatePrediction(dt)`，而该帧的 `tickDelta` 都是接近 0 的小值：

```java
float delta = tickDelta - this.lastTickDelta;   // 相邻 tick 的首帧 tickDelta ≈ 0.016 → delta ≈ 0
```

`dt ≈ 0` → 预测几乎不前进。剩下的只有每 tick 一次的 20% 校正：

```java
this.predX += (targetX - this.predX) * 0.2;
```

这是一个时间常数 ≈ 5 tick（0.25 s）的指数滞后 —— 高速方块在渲染上会"落后好几个方块"，
再叠加 R1 的双源切换，视觉上就是剧烈抽搐。

### R3 · 静止方块持续微抖 + `settled` 是死代码

```java
if (speedSq < 0.04) { lowSpeedTicks++; if (lowSpeedTicks > 10 && !settled) settled = true; }
```

`settled` 被算出来但**全文件没有任何地方读它**，注释里承诺的"停止同步防震荡闪烁"从未生效。
与此同时预测每帧无条件加 `g·dt²`，静止方块每帧下沉、每 tick 被拉回 20% → 周期性微抖。

### R4 · 客户端角速度从未到达客户端

```java
physics.setClientPhysicsParams((float) gy, (float) linDamp, (float) angDamp, angVx, angVy, angVz);
```

这些是**普通 Java 字段**，且方法只在服务端实体实例上被调用。
客户端实体由 spawn 包用工厂构造函数创建，`predAngVx/Vy/Vz` 恒为 0
→ 旋转预测空转，且渲染旋转同样在"predRot"与"slerp 结果"之间切换 → 旋转也在抽。

### R5 · 静态碰撞体注入"到达上限即整体放弃"

```java
for (class_2338 splashPos : splashBlocks)
    for (int dx = -radius; dx <= radius; dx++)
        for (int dy = -radius; dy <= radius; dy++)
            for (int dz = -radius; dz <= radius; dz++) {
                if (injected.size() >= maxStatic) return;   // ← return，不是 continue/break
                ...
            }
```

- 遍历量是 O(N·r³)：300 方块 × 17³ = **147 万次**，其中绝大多数是"区域内部"的无意义位置；
- 一旦累计 2000 个就 `return`，**排在后面的飞溅方块完全没有地面** → 穿过地面坠入虚空 →
  在极低 Y 处反复弹跳，看起来就是"不受物理控制地抽搐"；
- 边长 8 的立方壳本身就有几千个位置，2000 的上限根本不够用。

### R6 · `applyAction` 非幂等 → 拖动时间轴会重复生成

BBS 的 `ActionPlayer.goTo()`：

```java
while (this.tick != tick) { this.tick += this.tick > tick ? -1 : 1; this.applyAction(); }
```

拖动播放头会**逐 tick 重放**所有 clip。而原 `applyAction` 每次都：

```java
UUID worldId = UUID.randomUUID();
PhysicsBackendWorld physicsWorld = PhysicsWorldRegistry.createWorld(worldId, ...);
```

→ 新建物理世界 + 在同一位置再生成最多 300 个刚体与实体。
**两套刚体在完全相同的位置出生，求解器立刻把它们炸开 —— 典型的高速随机抽搐。**

### R7 · 物理挂在 `END_SERVER_TICK`，违反回放规则 ★核心（针对"短片"）

```java
ServerTickEvents.END_SERVER_TICK.register(server -> { ... PhysicsWorldRegistry.tickAll(1.0/20.0); });
```

BBS 的 `ActionPlayer.tick()` 在 `playing == false` 时**提前 return**，不再推进回放时钟，
但真实服务端 tick 照跑 → **暂停回放时方块仍在继续下落**，无法拍定格镜头；
拖动时间轴时物理已经跑到别处；导出视频时物理与渲染脱钩 → 不可复现。

`ActionClip` 其实已经提供了正确的挂载点：`applyRange()`（片段覆盖的每个 tick 都被调用，
且只在回放时钟推进时调用），原实现完全没用它。

### R8 · 本插件 spawn 的实体没有任何人回收

BBS 的 `DamageControl` 只在 `World.setBlockState` 处记录**方块变更**（`WorldMixin`），
实体只由 `ActionRecorder`（录制玩法操作）记录，**不包含回放期间由插件 spawn 的实体**。

于是每次回放停止：方块被恢复了，但几百个物理方块实体留在世界里继续下落、堆叠。
下一次拍摄在这个基础上再叠一套 → 越来越乱。

### R9 · native use-after-free（抽搐 + 偶发崩溃）

```java
// PhysicsBlockEntity
if (this.bodyHandle == 0 || this.physicsWorld == null) return;
this.physicsWorld.getBodyTransform(this.bodyHandle, _tmpPos, _tmpRot);
```

`PhysicsWorldRegistry` 会在「空世界」或「存活超过 1200 tick」时销毁世界（`nDestroyWorld`，
worldPtr 被释放）。**但实体不会随世界一起消失**：它的 `physicsWorld` 引用仍指向已关闭的对象、
`bodyHandle` 仍是旧句柄；实体自己的 `MAX_LIFE` 也是 1200 —— **两把闸刀同一 tick 落下，存在竞态**。

一旦世界先关，后续 `getBodyTransform` 就是在**已释放的指针上取数** →
返回垃圾坐标 → 实体瞬移、疯狂抽搐，严重时直接崩溃；
`PhysicsBlockEntity.remove()` 里的 `removeBody` 同样是 use-after-free。
`NativePhysicsWorld` / `JoltPhysicsWorld` 的读取方法当时**都没有 `isValid()` 保护**。

### R10 · 组合片段的子效果物理不会被驱动（修复过程中新发现）

`BlockSplashComboActionClip.applyAction` 是这样触发子效果的：

```java
subClip.applyAction(actor, player, film, replay, this.tick.get() + sub.startTick.get());
```

BBS 只认识 combo 片段本身，子片段是**直接调用**的 —— 因此 BBS **不会**替子片段调用
`applyRange`。把物理改由 `applyRange` 驱动后，若不同步转发，子效果的物理世界会永远停在
`localTick = 0`，方块僵在半空不动。

**这是本轮改动引入的真实回归风险，已同步修复**：combo 新增 `applyRange` 转发
（传入当前回放绝对 tick，子片段自行换算局部 tick）。

### R11 · 组合片段强度缩放"连乘"

```java
double origPower = splash.power.get();
splash.power.set(origPower * s);      // 非幂等
```

子片段是**持久实例**（内嵌在 SubEffect 里、随影片存档），而 `applyAction`
每次回放/每次拖动时间轴都会重新触发 —— 力度随触发次数**连乘**，
播放 5 次后飞溅会猛烈到失控。已改为「基准值缓存 + 外部修改检测」的幂等实现。

### 3.1 核心修复的数学表达

位置插值（节点位于 `t = -1, 0, +1`，即最近 3 个权威 tick 样本 a / b / c）：

```
p(τ) = a·τ(τ-1)/2 + b·(1-τ²) + c·τ(τ+1)/2      τ = tickDelta ∈ [0,1]
```

性质：

- **对恒定加速度精确** —— 自由落体是二次曲线，插值曲线与真实轨迹完全重合
  （线性 lerp 的误差是 O(T²)，这正是"看起来只有 20 帧"的来源）；
- **纯函数、无累积状态** → 不可能漂移、不可能发散；
- **与帧率无关** → 实时预览 / 165Hz / BBS 离线导出逐帧一致；
- **零额外带宽** → 不需要同步速度。

旋转：`prevQuat.slerp(currQuat, tickDelta)`，并对新四元数做 `q / -q` 符号修正
（点积为负则翻转，否则 slerp 会走"远路"造成旋转抽帧）。

### 3.2 渲染矩阵的正确写法

MC 渲染实体的矩阵原点（`WorldRenderer#method_22977`）是：

```java
base = lerp(tickDelta, entity.lastRenderX, entity.getX())
```

而 `FallingBlockEntityRenderer` 内部还会 `translate(-0.5, 0, -0.5)` 再画 0..1 的模型，
即方块中心 = `(baseX, baseY + 0.5, baseZ)`。因此必须用**同一个 base** 做抵消：

```java
matrices.push();
matrices.translate(renderCenterX - baseX, renderCenterY - (baseY + 0.5), renderCenterZ - baseZ);
matrices.translate(0, 0.5, 0);
matrices.multiply(renderRotation);          // 绕方块几何中心旋转
matrices.translate(0, -0.5, 0);
super.render(...);
matrices.pop();
```

## 四、回放规则对齐表

| BBS 规则（源码位置） | 修复后的行为 |
|---|---|
| `ActionClip.apply()`：`applyRange` 每 tick 调用，`applyAction` 只在 `relaive == 0` | 规划/执行彻底分离：`applyAction` 只建世界，`applyRange` 只推物理 |
| `ActionPlayer.goTo(from, to)`：逐 tick 重放所有 clip | `applyAction` 幂等（worldKey 命中即返回）；`applyRange` 逐 tick 推进，方向由 tick 差自动决定 |
| `ActionPlayer.tick()`：`playing == false` 时提前 return | 暂停 → `applyRange` 不被调用 → 物理定格 |
| `ActionPlayer.stop()`：所有结束路径的唯一汇聚点 | `ActionPlayerStopMixin` 在此销毁本插件的世界与实体 |
| `DamageControl` 只记录方块变更 | 本插件实体由自己负责回收（互补而非重复） |
| 导出视频按固定帧率离线渲染 | 物理由回放 tick 决定、渲染与帧率无关 → 可复现 |
| 组合片段直接调用子片段（绕过 BBS 时钟） | combo 的 `applyRange` 逐 tick 转发给活跃子片段 |

## 五、使用上的行为变化（需要注意）

1. **物理的存续范围 = 片段的长度。** 片段结束后 `applyRange` 不再被调用，物理随之停止
   （这是 BBS 的语义：clip 就是效果的窗口）。需要更长的演出，请把片段拉长。
2. **`solidify = true`** 的方块现在会一直留在地上堆着，直到回放停止；
   旧版会在 60 秒后被强制移除。
3. **`solidify = false`** 的存活上限改由 `animationDuration` 决定（以回放 tick 计；**暂停不计寿命**）。
   注意：sable/jolt 模式下没有"缩小消失"的渲染动画，到期是直接消失；
   需要缩小动效请用原版（`engine = vanilla`）路径。
4. **向后拖动时间轴**会触发一次"重建刚体 + 重新模拟"，300+ 刚体的场景会有轻微卡顿，
   已用 60 步/次的预算限制最坏情况。

## 六、验证

编译验证（无需 Loom，用仓库已有的独立 javac 流水线）：

```bash
# 需要一个 JDK21（Loom 用的那个）与 MC/Fabric/BBS 依赖 jar
javac -encoding UTF-8 --release 17 -proc:none \
  -cp "minecraft-intermediary-aw.jar;fabric-api.jar;fabric-api-modules/*;fabric-loader.jar;\
joml.jar;sponge-mixin.jar;asm*.jar;joltjni-win64.jar;lwjgl*.jar;brigadier.jar;\
datafixerupper.jar;bbs-2.5.2-1.20.1.jar" \
  -d out @sources.txt
```

> `-proc:none` 是必须的：Mixin 注解处理器在没有 obfuscation mapping 的纯 javac 场景下
> 会对 BBS 自身的类（`ActionPlayer.stop` 等）报 "Unable to locate obfuscation mapping"，
> 这是运行期才需要的映射，编译期应关闭注解处理。

**本次结果：62 个源文件、75 个 class，0 错误。**

游戏内回归建议（按优先级）：

1. 建一个小建筑（10×6×10），`block_splash` + `engine=jolt`，播放 → 方块应沿抛物线自然飞出、落地翻滚；
2. 拖动播放头来回扫过片段 → 不应出现方块数量变多、不应出现重叠挤压；
3. 播放中暂停 → 方块应立即定格；
4. 反方向拖动 → 方块应按"重新模拟"回到正确位置；
5. 停止回放 → 世界里不应残留任何方块实体（`/kill @e[type=bbsblocksplash:physics_block]` 应为 0）；
6. 反复播放 10 次 → 内存与帧率应稳定（观察 F3 的 entity 数与 GC）。

2. **`PhysicsRecordingManager` 已经按 tick 记录了完整物理帧**（位置/速度/四元数/角速度/方块状态），
   这正是"物理烘焙成关键帧动画"的原料。当前只在回退重放时用初始条件重建，
   可以进一步改成"直接读取记录帧还原"，把倒拖的成本从 O(步数) 降到 O(1)。
3. **`PhysicsEngine`（纯 Java 回退）与 `PhysicsEntityManager` 目前没有调用方**，属于历史遗留，
   可考虑删除或在原版路径真正接入。
4. `BlockShockwaveScheduler` / `BlockSplashReverseScheduler` / `BlockPathScheduler`
   仍挂在 `END_SERVER_TICK` 上，同样有"暂停回放不停止"的问题。
   本次未改动它们（避免扩大风险面），但它们应同样迁移到 `applyRange` 体系。
5. 组合片段（`BlockSplashComboActionClip`）本次已补齐 `applyRange` 转发。
   但要注意它传入的是**组合片段的绝对 tick**，子片段自行换算；
   若今后给 combo 增加"子效果循环/嵌套组合"，这套换算需要重新审视（嵌套两层时
   中间层必须继续转发，否则又会出现"物理不动"）。
6. `BlockSplashRecoveryManager` 仍按维度累积记录（已去重但不清空）。
   若 `DamageControl` 被用户在 BBS 设置里关闭，这些记录就是唯一的存档保险；
   开启时它们是冗余的。可以考虑在回放正常停止后清理，但需要先确认 `stopDamage`
   的执行顺序（本次选择了保守做法，不冒险）。
