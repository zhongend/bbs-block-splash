## 0. 审计方法：先立公理，再找反例

不做"逐行看代码猜 bug"，而是先把插件的运行约束固化成可证伪的公理，再用代码去撞它们。
**凡是与公理冲突、且能构造出具体触发路径的，才判定为缺陷**；构造不出反例的一律不报（避免"可能/也许"式的噪音）。

| # | 公理 | 来源 | 被违反的后果 |
|---|---|---|---|
| A1 | 服务端 20 TPS 的 tick 结果是**唯一权威** | MC 网络模型 | 客户端自算 → 漂移、两端打架 |
| A2 | 渲染帧率与逻辑 tick **无关**（BBS 导出是任意帧率） | BBS 导出流程 | 依赖逐帧 dt → 导出与预览不一致 |
| A3 | 网络不可靠，**任何"预测+校正"闭环都是正反馈** | 控制论 | 丢包 → 抖动被放大 |
| A4 | **回放时钟是唯一时间轴**（`applyAction` 规划 / `applyRange` 执行） | BBS `ActionPlayer` | 暂停时物理仍在跑 |
| A5 | `applyAction` 会被 BBS **逐 tick 重放**（`goTo` 拖动） | BBS `Replay.applyActions` | 非幂等 → 重复生成/累积 |
| A6 | 所有随机数必须**固定种子**、单线程求解 | 回放可复现 | 同一回放两次结果不同 |
| A7 | BBS `DamageControl` **只记录方块变更，不记录插件 spawn 的实体** | 宿主源码 | 实体无人回收 → 越播越乱 |
| A8 | `native` 指针释放后任何访问都是 **use-after-free** | JNI 语义 | 垃圾坐标 → 瞬移/抽搐/崩溃 |

**证伪门禁**：每条候选缺陷必须回答"在什么具体操作下会真的发生"，否则降级或剔除。

## 1. 结论摘要

共确认 **23 项缺陷**，其中 P0 × 2、P1 × 13、P2 × 6、P3 × 2。
**已全部修复**，编译零错误。

用户报告的核心症状「方块不跟随物理运动、随意抽搐」是 **4 个独立缺陷叠加**的结果
（§3.1 双数据源逐帧切换、§3.2 预测积分被冻结、§4.1 Accessor 失效、§4.2 跨端物理打架），
不是单一原因 —— 这解释了为什么此前的单点修补总是"修好一个又冒一个"。

## 3. 「抽搐」的根本原因（第一性原理推导）

### 3.1 位置有两个数据源，逐帧轮换

原实现引入了一个 `tickAdvanced` 标志，语义是"本 tick 是否已消费过预测值"：

```
每 tick 开始：tickAdvanced = false
渲染每帧：if (!tickAdvanced) { 用预测值; tickAdvanced = true; }
          else              { 用 lerp 值; }
```

**60 FPS ≈ 每 tick 渲染 3 帧**，于是：
- 第 1 帧 → 预测值
- 第 2、3 帧 → lerp 值

预测值与 lerp 值是两个不同的数（预测是二次曲线，lerp 是直线），
方块位置就以 **20Hz 在两个数值之间来回跳** —— 这正是肉眼看到的"随意抽搐"。

> 这不是精度问题，是**结构问题**：任何"多数据源 + 按帧轮换"的设计都必然产生周期性跳变。

### 3.2 预测积分其实几乎没跑

同一份代码里，预测积分只在**每 tick 的第一渲染帧**执行一次，而那一帧的
`tickDelta` 增量 ≈ 0（因为上一帧刚把 `lastTickDelta` 置为当前值）：

```
dt = tickDelta - lastTickDelta ≈ 0   →   位置几乎不前进
```

剩下唯一的实际作用就是「每 tick 以 20% 比例向服务端值靠拢」（时间常数 0.25 s）。
也就是说：**"高频预测"退化成了一阶滞后滤波器** —— 既是抖动的第二个来源，又让高刷屏完全没有收益。

### 3.3 正确答案（已实施）

对**最近 3 个权威 tick 样本**做二次拉格朗日插值：

$$p(\tau)=a\cdot\frac{\tau(\tau-1)}{2}+b\cdot(1-\tau^2)+c\cdot\frac{\tau(\tau+1)}{2}$$

- 对自由落体（恒定加速度）它是**精确解**，不是近似；
- 纯函数、无状态、无积分 → **与帧率完全无关**；
- 只读服务端权威值 → 没有正反馈回路，丢包也不会放大。

旋转改用最近 2 个四元数 `slerp` + `q/-q` 符号修正（避免取到长弧）。
渲染器用 `lerp(tickDelta, entity.field_6038/5971/5989, getX/Y/Z())` **抵消** vanilla 已施加的
矩阵原点，否则 offset 会随 `tickDelta` 摆动 —— 又是一个抖动源。

## 4. 三类"隐形"缺陷（最难定位的部分）

### 4.1 `@Accessor` 被 vanilla 同名方法"满足"而完全失效

`EntityAccessor` 原本把读取方法命名为 `isOnGround()`，与 `Entity.isOnGround()` 完全同名同签名。

> Mixin 语义：若接口方法能被目标类的**既有方法**满足，`@Accessor` 就不会生成实现。

于是 `((EntityAccessor) x).isOnGround()` 实际调用的是 vanilla 方法。
而 `BbsEntityMixin` 为了骗过"落地变方块"判定，**把 vanilla `isOnGround()` 对 NO_SOLIDIFY 实体强制返回 false**。

**后果链**：物理层读到的 `onGround` 恒为 false → 落地检测失效 → 弹跳、地面摩擦、旋转平滑归零**全部不执行** → 方块看起来"完全不受物理控制"。

修复：全部访问器加 `bbs$` 前缀（`bbs$isOnGround()` / `bbs$setOnGround()`），
并在类注释里写明这个历史教训，防止后人"清理"掉前缀。

### 4.2 单机环境下客户端与服务端共享同一张 `static` 物理表

`RotatingFallingBlockManager.physicsStates` 是 `static Map<UUID, PhysicsState>`，
而**单机（集成服务器）下客户端与服务端实体在同一 JVM、UUID 相同**，
且 `IS_ROTATING` 会经 DataTracker 同步到客户端。

原 `FallingBlockEntityPhysicsMixin.onTickEnd` 没有端侧判断 → 客户端 tick 也会：
1. 命中服务端的 `PhysicsState` 并**重复施加**速度/位置；
2. 在"实体已移除"分支调用 `removePhysics(uuid)`，**把服务端状态删掉**。

结果：两端物理互相打架，方块抖动、瞬移、状态凭空丢失。

修复：在物理入口加 `if (tickWorld == null || tickWorld.field_9236) return;` —— **物理只在服务端推进**。

### 4.3 「碰撞快照」覆盖「碰撞结果」

`handleGroundBounce` / `handleWallBounce` / `resolveBlockStuck` 都会通过 `setVelocity` 改写实体速度，
但 `velocity / speed / horizontalSpeed` 是**碰撞发生之前**取的快照。
后续的地面摩擦与空气阻力代码用旧快照回写：

```java
self.method_18800(velocity.x * friction, velocity.y, velocity.z * friction);  // ← 旧 y
```

刚设置的**弹跳 Y 速度与撞墙反弹速度被整体覆盖** → 落地不再弹起、撞墙不再反射，
方块表现成"粘"在地上。

修复：碰撞处理结束后**重新读取** `self.method_18798()` 再计算摩擦与阻力（源码中标记为"2.8 重新读取速度"）。

### 6.3 回归风险与行为变化（需你确认）

修复后有 **3 处刻意的行为变化**，都是"对齐 BBS 语义"的必然结果：

1. **物理存续范围 = 片段长度**。物理由 `applyRange` 驱动，片段结束即不再步进。
   需要更长的演出，请**拉长片段的 duration**（这是 BBS 的正确用法）。
2. **`solidify=true` 的方块保留到回放停止**（旧版会在 60 秒时被强制移除）。
3. **未改动 `gradle.properties` 版本号**（仍为 `2.1.0`）。本次是**行为变更**，建议升到 `2.2.0`。

## 7. 未修复项 / 后续建议

### 7.1 三个调度器同样挂在 `END_SERVER_TICK`（同源问题，本轮未动）

`BlockShockwaveScheduler` / `BlockSplashReverseScheduler` / `BlockSplashAnimationScheduler`
依然由**墙钟**驱动，因此**暂停回放时它们仍在推进**（与 §3 已修的物理不同）。

本轮未改动是**刻意的风险控制**：这三者是"方块位移 + 变方块"的效果，
改为回放时钟驱动需要重做它们的状态机与恢复逻辑，属于独立改造。
**建议下一轮单独处理**，方案与物理层一致：`applyAction` 规划 + `applyRange` 执行。

### 7.2 遗留死代码（P3，无运行时风险）

- `actions/physics/PhysicsEngine.java`、`PhysicsState.java`、`PhysicsEntityManager.java`
  无任何调用方（`PhysicsBlockEntity.getPhysicsState()` 已 `@Deprecated` 返回 `null`）。
- `PhysicsWorldRegistry` 的 `tickAll` / `createWorld×4` / `getWorld` / `destroyWorld`
  已是 `@Deprecated` 兼容壳。

**建议**：直接删除，或至少在类头标注"未接线，勿在此基础上开发"。
特别是 `createWorld` 系列会**返回未注册的 native 世界**，一旦被误用即泄漏。

## 8. 一句话总结

> **抽搐不是"调参问题"，是四处结构性缺陷的叠加**：
> 渲染位置在双数据源间逐帧轮换、预测积分被冻结、访问器因重名而失效、两端共享物理状态互相打架。
> 修复思路统一为一条原则 —— **服务端 tick 是唯一权威，客户端只做数学插值，物理只由回放时钟驱动。**
